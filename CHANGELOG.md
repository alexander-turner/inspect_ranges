- `range_apparatus`, a deterministic "is my range working" checker for range developers, ships as the first member of the new public `inspect_ranges.scanners` module, built on the new `inspect-scout` dependency (>= 0.6.0), which bumps the pinned `inspect-ai` floor from 0.3.266 to 0.3.282 (scout's requirement; depending on the latest inspect-ai is deliberate). It is an `inspect_scout` scanner, so one implementation covers both consumption paths: after the fact over finished logs (`scout scan inspect_ranges/range_apparatus -T ./logs`, resolvable by name through the entry-point registry, or `inspect_scout.scan` from Python) and online in a task's scorer list via `inspect_scout.as_scorer`, where findings land beside `challenge_scorer` in the normal log view. The score value is the finding count (0 is healthy; `mean()` metric, no accuracy semantics), the explanation carries one line per finding with a remediation hint, and the structured findings (stable detector id, severity, message, hint, event references) ride the score metadata. Four deterministic detector families, every signature mined from the real provider/channel/challenges code and deduped per sample: plumbing (post-readiness vsock/channel failure strings with the boot-time `up-readiness` lines excluded, three-plus retries against one guest, evidence finalize/teardown error lines, the in-guest tool's rc 124/125 stderr contract), config-aware reachability (armed by the optional `range_spec` argument, taking the same forms the provider accepts: connectivity failures in tool output toward addresses the spec declares reachable from the foothold, computed from the compiler's own allocation and endpoint classification under the nftables first-match contract, single router hop by design; and private-range addresses in commands that belong to no declared network, public addresses never flagged), `verify_goal` behavior (the zero-recorded-submissions condition behind the scorer's loud warning, scoped to challenges with submission-taking goals; submissions whose result says the goal id binds to nothing; `candidates_dropped` in the recorded score; completion claims in the final assistant message over never-attempted submission-taking goals; the mid-run scorer-invocation marker), and scoring/evidence integrity (recorded validity other than `valid` with its reasons, corroboration flags or incomplete coverage on an otherwise valid sample, and the thresholded hint when every achieved goal with a declared segment reads `corroborated` false, pointing at capture chunk rotation and cleartext flow). The scoring-integrity detectors read the recorded score from `ScoreEvent`s with a store-record fallback and stay quiet when neither exists, so running the scorer form before `challenge_scorer` is safe (cross-scorer ordering is not a contract). Validated against the real 2026-10-21 publish-day logs: zero findings on the green dmz-pivot (scanned with its real range spec) and cyris evals through both the engine seam and scout's own loader, and a genuine fire pinned on the mh-build log, whose achieved exfiltrate goals uniformly read `corroborated` false. - Image catalog (standard-images-v1): the standard images publish under `docker.io/meridianlabsai`, each consumable by bare name and pinned by digest. The `attack` image is the kali-class attack box (nmap, netcat/socat, tcpdump, impacket, sqlmap, hydra, john, gobuster, ffuf, smbclient, ldap-utils, and metasploit from its official repo with the release key fingerprint-pinned), recipe-built over the noble golden with the delivered package set recorded in-image (`/etc/attack-image.manifest`) and a build-failing zero-non-loopback-listener containment invariant. A dedicated attack box that declares no `image:` now boots it by default (migration: such attackers previously booted the default guest image; declare `image: ubuntu-noble` to keep the old behavior). `inspect-ranges publish` promotes built guests (`--guest/--as`), goldens (`--golden`), and the daemon artifact (`--daemon`) to a location whose catalog list updates with each image; `daemon-bundle --pull` fetches the published daemon artifact without a Go toolchain, and both the catalog list and the daemon bundle travel with whole-location mirrors. Eval init now pulls catalog images implicitly too (the attacker default, bare-name goldens), so a clean machine's first eval needs no explicit fetch verbs and warm evals still cost zero network. Fleets pin with `images pin` (names to root digests, consumed as `@sha256` pins) and pin the hardened range container image itself with `INSPECT_RANGES_RANGE_IMAGE=repo@sha256:...` (pulled once by `up`; mutable tags refuse; the local build stays the default and the dev loop) (docs: Image Catalog, Distribution).

- Distribution (distribution-v1): built ranges publish and consume across three interchangeable location forms (the public hub, private OCI registries, and plain OCI-layout directories for the air gap), joined to specs by the normalized-spec hash. `inspect-ranges push` publishes a build's transitive closure (dedup by digest); bare `pull` resolves the build matching the local `range.yaml` exactly (refusing `no-build-for-spec` with the nearest published build named) and `pull name@sha256:...` works with no spec in hand; the provider pulls implicitly at eval init with docker-pull-shaped progress and clean prerequisite refusals, warm evals cost one hash and zero network, and `INSPECT_RANGES_NEVER_PULL` pins a host against implicit transfers. Catalog images fetch via `images pull` (sticky) and move forward only via `images refresh` (whole chain, atomically staged). `mirror` seeds or syncs whole locations (every published build, not just latest), moves single builds spec-driven for the cross-group case, and the directory form tars across air gaps with everything still verifying. `images prune --chains` reclaims unreferenced golden/vendor chains under a cache-wide lock shared with every landing path, never a backing from under a dependent; `up` now verifies the full backing chain including the golden-to-vendor edge, so a mixed cache refuses instead of booting silently; doctor gains Distribution rows. The search path is `INSPECT_RANGES_REGISTRY` (ordered, first match wins, deployment registries shadow public names deterministically; a broken location aborts rather than silently de-shadowing). Proven live by five batteries plus a recorded conformance run against the real Docker Hub (production token flow, presigned-storage redirects with the bearer token stripped cross-origin, measured anonymous rate limits), and the Journey B transcripts executed as the phase exit (docs: Distribution).

- Docs: a dedicated [Custom Goals](goals.qmd) article covers creating new goal types (the `GoalType` contract, the oracle surface, proof-design rules, assurance labels, testing, and registration); the Challenges article's section now points there. The closed v1 `challenges.yaml` type union is recorded in the article's registration section as the open concern.
- Every QEMU guest runs as its own unprivileged uid (issue #5): a per-domain static DAC seclabel (`GUEST_UID_BASE + cid`, the Cloud Hypervisor scheme) carries the per-VM boundary; `security_driver = "none"` stays and disables only the MAC slot, since sVirt AppArmor cannot load per-VM profiles inside the hardened container (the outer jail denies CAP_MAC_ADMIN and securityfs by design), which is now documented where the setting lives. The boot script pre-owns each guest's overlay, seed, and console log; libvirt never chowns a shared backing golden.
- The agent-containment section-6 defender-to-agent negative checks are automated (issue #6): the build's proof boot runs a `conformance` stage before the behavioral checks (a shared-segment defender TCP-sweeps the attacker; the attacker checks reserved hypervisor addresses answer nothing beyond their allowed service and unreserved gateway candidates are silent), and any finding refuses the manifest. Scope: TCP only, dedicated attack boxes only (foothold ranges skip the stage).
- BREAKING: the sandbox provider is registered as `range` (was `libvirt_range`, with no alias kept): `sandbox=("range", "range.yaml")`. The old name described an implementation detail that no longer covers the default attack box, which boots under Cloud Hypervisor with no libvirt in its path.
- The range container's segment bridges no longer have IPv6: the rendered compose sets `net.ipv6.conf.default.disable_ipv6=1` in the range's network namespace, so the bridges and taps created after it send no router solicitations, MLD or DAD frames and do not answer `ff02::1`; the bridges are also created without multicast snooping, so they send no IGMP report of their own and flood multicast to every port, like a plain switch. Guest-to-guest IPv6 still crosses the bridges; the host's IPv6 setting is unchanged.
- Guests no longer get q35 legacy devices that no configuration names and no guest uses: the domain XML turns off the VMware backdoor port and the HPET natively, and the SATA AHCI controller, SMBus (with its SPD EEPROMs), i8042 keyboard controller and kvmvapic through QEMU arguments (libvirt 10.0 has no elements for them). The PIT and PIC stay on.
- Hosts and routers gain a `vmm: qemu | cloud-hypervisor` field (default `qemu`); the agent/attacker box now defaults to `cloud-hypervisor`, so an existing range's attacker box moves from QEMU to Cloud Hypervisor (declare `vmm: qemu` on the attacker to keep QEMU). A Cloud Hypervisor guest boots directly from the boot script as an unprivileged per-guest uid with no domain XML and is reached over its hybrid-vsock Unix socket with an `SO_PEERCRED` peer check, and the range image carries the pinned Cloud Hypervisor binary and firmware (docs: Sandbox Provider). Migration notes: the new field changes the normalized spec form, so build manifests recorded before this release fail the gate's spec-revision match and consumers refuse until one rebuild per range (guests are reused: build keys do not include the field; declaring `vmm: qemu` on the attacker reproduces the pre-flip hash exactly, keeping an existing manifest valid). A foothold attacker (`host:` set) now refuses ANY declared `vmm`, including a redundant `vmm: qemu` that previously validated.
- Challenges: `challenges.yaml` defines what an agent is asked to do and how success is verified; `challenge_dataset()` builds the Inspect dataset (validated against the range), `challenge_setup()` plants per-sample proof material and starts observers, `challenge_scorer()` verifies and aggregates with validity states. Fourteen goal types ship (flag, answer, exfiltrate, execute, control/privilege, hijack, degrade, tamper, availability, detection, evade, judge, patch), proofs anchored by per-sample secrets, a nonce-bound active prober on a clamped probe endpoint, exported telemetry, and evidence corroboration that can invalidate a sample on contradiction but never fails one on missing coverage (docs: Challenges).
