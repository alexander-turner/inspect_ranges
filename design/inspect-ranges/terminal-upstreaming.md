# Direction: moving the terminal tool into inspect_ai proper

Status: possible future direction (recorded 2026-10-24, not scheduled). No code change in either repo yet; this note holds the obstacle analysis and the plan shape so the work can start from decisions, not archaeology. Companion to [terminal-tool-v1.md](terminal-tool-v1.md), whose follow-ups list recorded "upstreaming the core to inspect_ai" when the tool was built.

## Why

The tool is now the documented react default here and its viewer half already lives upstream: inspect_ai's sample view plays `asciinema:*` store keys (ts-mono #814). Upstreaming the tool itself gives every inspect_ai user named tmux sessions with in-viewer playback, and gives us something better than we have: direct integration can couple privately to the sample lifecycle, so the cast lands in the store even for interrupted samples, an edge the current design accepts losing (deferred teardown outside the store context, the `_current_store` weakref resolving dead).

## What the inventory says

The "against only public inspect_ai surfaces" discipline held, so the split is clean:

- **Near-clean lift (644 of 923 source lines).** `_terminal/session.py` (pure tmux mechanics), `_terminal/cast.py` (asciicast assembly and clipping), `_terminal/tool.py` (the tool). Their only inspect_ranges imports are `GUEST_BRAND` (deriving the sink dir `/tmp/.guestd`, one constant to rename) and import paths. `tool_state_instance` / `tool_state_scope` are already inspect_ai public API; we just import them through a private module path. The pure test file (`tests/test_terminal_session.py`) and the live-tmux tool tests (`tests/test_terminal_tool.py`, already tmux- and CI-gated) travel essentially unchanged. The terminal-bench attribution travels as the `session.py` module docstring, which matches inspect_ai's "Adapted from" convention (the text_editor precedent).
- **All coupling concentrates in `_terminal/capture.py` (274 lines)** behind one gate: `_capture_target()` lazily calls `sample_handle_for(sandbox())` and returns `(recording, evidence, project)`. The evidence surface consumed is three members (`append_driver`, `register_producer`, `location`). The constructs that exist only to serve ranges' deferred teardown are `_PROJECTS`, `finalize_terminal_captures(project)` (sole caller: provider `_destroy`), and the `_current_store` weakref.
- **Upstream has a natural home.** `src/inspect_ai/tool/_tools/_terminal.py` as a sibling of `bash_session`, a `## Terminal` section in `docs/tools-standard.qmd`, `### terminal` in the tool reference, fast tests on the bash_session monkeypatch template.

## Obstacles and how to surmount them

1. **Capture transport.** inspect_ai's default `exec_remote` injects the sandbox-tools PyInstaller bundle into the sandbox and runs an RPC server there; the base-over-exec implementation [terminal-tool-v1.md](terminal-tool-v1.md) describes was already gone by the version we pin (checked 2026-10-25: 0.3.282 injects, so the v1 fleet pass recorded every cast over the injected transport on real range guests, and the posture question is settled de facto, injection works on the foothold). Streaming the pipe-pane sink is impossible over plain `exec` (it buffers until exit), so the remaining decision is only whether to keep riding injection or to build the already-recorded follow-up, a native channel-backed `exec_remote` override on `RangeSandboxEnvironment` (smaller guest footprint, no bundle on the attack box; worth doing but no longer a blocker or a new risk).
2. **tmux as an image prerequisite.** inspect_ai's current philosophy is "no image prerequisites" (bash_session injects everything it needs). `terminal()` deliberately requires tmux. Surmount by documenting the requirement with a crisp absent-tmux error and positioning against bash_session (one injected PTY vs multiple named sessions on what the image provides). Needs explicit maintainer blessing as a deviation, not code.
3. **No end-of-sample hook for tools.** `Hooks.on_sample_end` fires after `log_sample()` with a read-only `EvalSample`; the store snapshot (`create_eval_sample`) happens after the sandbox context exits; the last safe moment is the shielded `finally` inside the sandbox context where `Task(cleanup=)` runs. Surmount with the private coupling: an internal sample-scoped finalizer registry drained in that shielded `finally` while the store is live and the sandbox is up. The in-tree tool registers one finalizer per sample that closes recorders and writes the `asciinema:*` casts. This deletes the `_current_store` weakref, `_PROJECTS`, and provider-owned finalize in one move, and closes the interrupted-sample cast loss (the shielded finally runs on cancellation too). This is the piece upstream review should camp on, since it touches the sample runner.
4. **The recorder seam (how ranges keeps its evidence without controlling the tool).** Upstream defines a small `TerminalRecorder` protocol fed by the tool's single pipe-pane tail: on_open, on_output(session, host_ts, raw bytes), on_marker, on_close, finalize. The tool ships a default recorder (assemble cast, write store key: today's behavior minus evidence). Discovery goes through the sandbox environment, not tool arguments: an optional method on `SandboxEnvironment` returns the recorder, default the built-in one. Placement rationale: the provider is exactly the party that knows about evidence, and task wiring never changes; `terminal()` gets evidence iff it runs on a range sandbox. `RangeSandboxEnvironment` returns a recorder wrapping the default that also mirrors raw chunks to the `terminal/<session>` evidence stream and writes the `.cast` file beside the evidence. Ordering stays ours: the provider owns its recorder and flushes it before `EvidenceSession.finalize()`. Keep the protocol tiny and byte-oriented so everything we record today is rebuildable from it; the rejected alternative (a global registry / entry point) adds registration lifecycle for no gain when the sandbox object is already in the tool's hands. The recorder contract also carries the agent-attribution header fields (2026-10-25): the default recorder captures the opening agent context at open time (`SessionOpener`: agent span id, denormalized agent name, tool span id) and emits them as additive `ir_*` asciicast header keys, so viewer grouping by agent works identically for upstream and ranges casts.
5. **Conventions and renames.** The cast store cap env var takes an inspect_ai name (or becomes a tool parameter); the sink dir drops the guestd brand; the `asciinema:terminal-<name>` key convention is already upstream (free). Default-namespace names stay byte-identical where cheap (evidence stream names, cast filenames); where not, it is a changelog-noted break in ranges' next release.

## The two-phase plan

**Phase 1, inspect_ai PR.** Port session/cast/tool, parameterize the sink dir, add the internal sample-finalizer registry and the `TerminalRecorder` protocol with the default store-cast recorder, move the pure and live-tmux tests, write the docs section and reference entry. Standalone value gate: any docker image with tmux gets named sessions plus in-viewer asciicast playback, no ranges involved.

**Phase 2, inspect_ranges release.** Bump the inspect_ai pin; delete `_terminal/{session,cast,tool}.py`; re-export `terminal` from inspect_ai so `from inspect_ranges import terminal` keeps working; rewrite `capture.py` as the evidence `TerminalRecorder` returned by `RangeSandboxEnvironment`, plus the native `exec_remote` override; retarget the capture tests at the recorder protocol instead of monkeypatched internals; re-home the docs prose that narrates behavior now owned upstream; mark the upstreaming follow-up executed in [terminal-tool-v1.md](terminal-tool-v1.md).

## Open decisions (to settle before Phase 1 starts)

- Recorder discovery: formal optional method on `SandboxEnvironment` (recommended above) vs something less visible. This is the only new provider-facing surface and carries the API-review weight.
- Whether Phase 1 ships with ranges' native `exec_remote` override landed first, or accepts bundle injection on the foothold in the interim.
- License handling for the Apache-2.0-derived port is a maintainer conversation held outside the repo.
