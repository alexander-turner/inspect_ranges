# inspect_ranges

Working folder for **`inspect_ranges`** — a new [Inspect](https://inspect.aisi.org.uk/) package for defining cyber range evaluations via a `range.yaml` format, backed by a new libvirt-based sandbox (Docker/Compose compatibility is a non-goal). Project opened 2026-09-30.

* **[Design and architecture review (draft 1)](architecture.md)** - the synthesis document for broader review: system overview, spec/networking/control-plane design with measured spike evidence, the full security analysis, deployment model, performance envelope, implemented-vs-designed ledger, and open questions

* **[External review triage (2026-10-04)](external-review.md)** - a fresh-context agent's 11 findings against the overview and records, each verified against the repo and triaged (accepted or qualified, none dismissed) with the action and artifact it produced

* [Small realistic cyber ranges — source survey](survey.md) - what public artifacts define small, realistic, quickly-runnable ranges with machine-readable configs; the six selected for the baseline; catalog of everything surveyed; finding: the full MHBench corpus is public, with a measured assessment
* [range.yaml — draft schema swag (v0.1)](range-yaml-swag.md) - the working strawman schema the six examples exercise: the L1–L9 range anatomy and D0–D5 defense spectrum, the networking-requirements table (each requirement → its libvirt realization → the example that forces it), and the attack_path concept mapped across surveyed formats
* [Decision (proposed): networking v0.2](networking-v0.2.md) - richer ACLs (host/CIDR endpoints, icmp, ordered deny), explicit routing (gateway election, static routes), scoped egress allowlists, dual-stack types behind per-construct gates — all under a lockstep rule (schema + validation + realization + booted conformance, or it stays out); the public spec API commitment (sandbox config as a `RangeSpec` object or a YAML path, types exported and documented); draft fixtures in [ranges-v0.2-drafts/](ranges-v0.2-drafts/)
* [Decision (proposed): guest configuration v0.3](guest-config-v0.3.md) - the layer-4 vocabulary (users, services-as-assertions, vulnerabilities/misconfigurations, data, defense, AD identity with typed ACL edges, provisioning by reference): converged-state declarations, parsed uniformly now, gated at planning until the build phase realizes them

* [Decision: own the libvirt sandbox provider](docker-provider-reuse.md) - why we write our own provider rather than reusing Inspect's Docker provider, what we give up, and which pieces we port (with attribution) vs rewrite

## Example ranges (development/testing baseline)

**Status: translated requirements fixtures** — each `range.yaml` validates against schema v0.1 and preserves upstream semantics, but none has been built or booted as a VM range (images are logical references; provisioning is deferred). Each directory holds `range.yaml` (our translation, draft schema v0.1), `challenges.yaml` (task prompts as example-dataset seeds — verbatim from the upstream ecosystem where tasks exist: KYPO training levels, Incalmo attacker prompts, cochise pentest scenario; tagged as ours where not), `notes.md` (per-field provenance, tagged defaults, to-verify items), and `upstream/` (the verbatim original source configs and prompts, so `inspect_ranges` code can see the originals, not just our translation).

* [vulhub-zabbix](../../src/inspect_ranges/examples/_vulhub_zabbix/notes.md) - 4 Linux hosts, flat network, real CVE (Zabbix SQLi→RCE); the minimal/smoke-test case
* [kypo-demo](../../src/inspect_ranges/examples/_kypo_demo/notes.md) - 2 hosts + explicit router across 2 routed subnets; static IPs, randomized variables (KYPO CRP)
* [cyris-basic](../../src/inspect_ranges/examples/_cyris_basic/notes.md) - firewall-gatewayed office/servers segments with per-guest task provisioning (CyRIS, KVM-native)
* [equifax](../../src/inspect_ranges/examples/_equifax/notes.md) - breach-derived 3-subnet enterprise with asymmetric ACLs and a planted SSH-key pivot (MHBench, CMU; formerly mhbench-equifax-small)
* [goad-light](../../src/inspect_ranges/examples/_goad_light/notes.md) - 3-VM Windows AD forest (parent+child domains) with seeded AD attack surface and Defender toggles (GOAD)
* [splunk-detection](../../src/inspect_ranges/examples/_splunk_detection/notes.md) - Splunk-instrumented Windows endpoint; telemetry as first-class config (Splunk attack_range; formerly attack-range-windows)
