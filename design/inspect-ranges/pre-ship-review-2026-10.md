## P0-1: the candidate cap does not hold at the poller (scoring gameable)

CONFIRMED (probe re-run by adjudicator). Claim: "At most 8 distinct values per goal are ever verified, earliest first... submission volume cannot amplify scoring cost, and since proof values are high-entropy, eight guesses buy nothing as an oracle" (docs/challenges.qmd:161; `CANDIDATE_CAP` docstring at engine.py:64 says the cap applies "BEFORE any verify work at both verification sites"). Actual: there are three verification sites, and the cap exists at two. `verify_goal` refuses to verify past the cap but still records the submission (verify.py:110,165-170); `GoalPoller._tick` (poller.py:195-243) then verifies EVERY distinct recorded value on its next tick, uncapped (`CANDIDATE_CAP` does not appear in poller.py), latching first-pass-wins; `latch` never downgrades an achieved record (engine.py:228-241), so the scorer's capped end-of-run pass cannot undo it. Probe: 60 wrong values plus the right one as #61, one tick, latched True; the latched pass survives a scorer pass over 8 wrong candidates. Failure scenario: any low-entropy goal (the kypo `answer` port residual named in challenges-v1.md, `choice`/small-int draws) is brute-forceable to a guaranteed pass by flooding `verify_goal`. Fix shape: apply the earliest-8 cut inside `_tick` (the dedup list is already built there), or stop appending past-cap submissions in `verify_goal`.

## P1-3: `cli_cleanup` ignores the lease's recorded origin

CONFIRMED (probe re-run: 2 passed). Claim: "Fresh-process cleanup from on-disk state" (provider.py:744), "removes every provider-origin project found in on-disk state... from any shell, after any crash" (docs/provider.qmd:100), leases' origin as "the self-describing teardown address: a fresh process re-resolves it by import alone" (docs/topology.qmd:114), and topology.qmd:57's promise that cleanup "fails loudly by design" when the applier is dead. Actual: `cli_cleanup` resolves its down seam once from the ambient `INSPECT_RANGES_HOST` (state.py:169) and never reads `lease.origin`; from a plain shell it runs the DIRECT local down, then releases the CID lease and deletes the host lease, the reaper's only retry anchor. The reaper itself refuses `origin-unresolvable` touching nothing (reaper.py:114-131), the exact discipline recorded when this bug class was fixed there, and attack-box teardown already resolves origin from disk. Failure scenarios: uds topology after a driver crash leaves the applier's admission charge and relay map stranded forever (lease deleted, reaper can never run); a custom separated backend gets a vacuous local "success" that deletes the lease over a still-running remote range. Fix shape: mirror `_reap_one` (resolve each target's lease origin, refuse unresolvable, route separated backends through their reclaimer; ambient env only for projects with no host lease).

## P1-4: a forged writer verifies OK under `--expect-seal`

CONFIRMED (unit probe + code entailment). Claim: the binding anchors "the seal tier itself (its fields, its presence, the record's location, the writer set)" (evidence-v1.md:21, reader.py:5); docs/evidence.qmd:48 "run `evidence verify --expect-seal` with the binding's digests and the full claim holds". Actual: `VerifyReport.ok` is "every writer present replayed cleanly" (reader.py:148-150); a writer present at the location but absent from the supplied binding is verified for internal consistency only and still counts toward `ok`, so additions to the writer set are never a break. The capture host's put-only credential can CREATE new keys (conditional puts refuse only rewrites), so a compromised host fabricates a new internally-consistent writer with forged streams and the documented full-guarantee command exits 0. Mitigations keeping this P1: scoring pins writer names on every read, and the human-readable output discloses "internal consistency only" per writer; the exposure is the machine verdict (exit code, `report.ok`, `--json`) that tooling trusts. Fix shape: when any `--expect-seal` is supplied, treat location writers absent from the binding as a break (the finalize-time binding is the complete writer set by construction).

## P1-5: `corroborated: false` is unrecordable after a mid-run latch

CONFIRMED (probe re-run). Claim: score metadata semantics distinguish "`false`: a declared observer found nothing" from "`null`: no corroborating observer was declared" (docs/challenges.qmd:226), with the page's own worked dmz-pivot sample showing `"corroborated": false`; poller.py:40 says corroborated "stays `None` UNTIL the scorer's full check". Actual: `latch` upgrades an achieved record only when the new result's corroborated is True (engine.py:228-241); the scorer's full-check False is discarded. On the common path (agent verifies via `verify_goal` mid-run, cheap tier reads no pcap, latch carries None; end-of-run check on the declared segment finds nothing) the final record reads `null`, erasing the reviewer-facing distinction and making the docs' own example unreproducible. Not score-affecting; corrupts the trust-labeling field. Fix shape: let a full-check result also settle None to False (one condition plus a test; the None-to-True upgrade is already pinned).

## P1-6: blocking sends break on trailing `&`, `&&`, and comments, with false status

CONFIRMED (probes re-run on real tmux). Claim: "block=True instead waits up to `timeout` seconds for the command to finish" (tool.py:165); the splice runs "`<command>; tmux wait -S <channel>`" (session.py:203), and `_trim_trailing_semicolons` exists precisely to prevent "a shell syntax error that never runs the command and stalls the send to its full timeout" (session.py:191). Actual: only trailing `;` is handled; `cmd &` and `cmd &&` splice into `&;`/`&&;` which is a bash syntax error, so the command NEVER RUNS, the send stalls the full timeout (default 180 s), and the result says "it may still be running"; a trailing `# comment` absorbs the splice so the command completes instantly yet the send still stalls full-timeout with the same false message; an unclosed quote leaves the session stuck at PS2 with harness text inside the pending string. Backgrounding a listener (`nc -lvnp 4444 &`) is a flagship workflow, so block+`&` is a plausible agent path, and the false "may still be running" corrupts the agent's world model while burning budget. Fix shape: extend the pre-splice validation (trim or refuse trailing `&`/`&&`/`||`/comments, refuse unbalanced quotes) with table tests; refusal strings already exist as the pattern.

## P1-7: the wait-channel echo leaks into model output at wrap boundaries

CONFIRMED (probe re-run; leak reproduced at pad 96-102). Claim: "Remove the blocking signal's pane echo from model-facing output... the model should read its own command, not the harness suffix" (session.py:235-239; same in CHANGELOG). Actual: `_WAIT_ECHO` is a single-line regex and `capture-pane` inserts a newline at the 160-column wrap, so whenever prompt+command length puts the ~41-char suffix across a wrap, fragments like `tmux wait -S done-w-...` land in the model-facing delta (roughly one in four wrapped long commands; long one-liners are routine). Fix shape: scrub across the wrap (join-then-match on the echo line's wrapped continuation, or scrub by channel token anywhere in the echoed region).
