# The build/images spine: image references, one invalidation algebra, and the artifact ledger

*Provisional answers to the three structural questions from [build-images-requirements](build-images-requirements.md) section 6 that are expensive to retrofit: Q1 (image reference grammar), Q2 (unified invalidation), and Q3's core (the artifact ledger and the two-manifest relationship). Everything else (scenario-vs-recipe, CLI verbs, distribution detail, orchestration) is decided inside the vertical slices where the tradeoffs are visible. These answers are deliberately minimal and remain revisitable at the generalization test: the vulhub slice is their first consumer, and the goad-light slice (Windows, checkpoints, the second consumer) may force revision while revision is still cheap. The five decision points of this memo (no tags with automatic freezing and explicit update; all-or-nothing verification caching; the checkpoint key with clean rebakes; the stale-bundle hint; the publish column and the two-manifest relationship) were each talked through and ratified by the user on 2026-10-17.*

## Q1. What `image:` means

**The grammar: `image:` is a logical name, optionally digest-pinned.** `name[@sha256:<hex>]`, where `name` is a lowercase slug (letters, digits, `.`, `-`, and at most one `/`). Nothing else is legal: no registry hosts (redirection is configuration, never spec content, per the disconnected-operation requirement), no version expressions beyond the digest pin, and no parameters.

**The namespace convention (user decision, 2026-10-17): bare names are the blessed catalog, prefixed names are group content.** Docker's `library/` convention, adopted: a bare name (`ubuntu-noble`, `kali-attack`, `windows-2019-dc`) is reserved for the project's standard catalog, published in the public org and enumerated by the Q12 vendor-catalog work; this is what gives the schema's promised defaults ("the backend's standard attack image") real referents. An `org/name` prefix (`acme/payroll-db`, `vulhub/zabbix-web`) marks group-authored content, namespaced by the publishing group, so cross-group mirroring imports another group's names under their prefix and can never collide with yours. The one-slash limit keeps the name-to-registry-path mapping trivial: bare catalog names map directly under the public org (Docker Hub's two-level repo structure), and prefixed names live in registries with nested paths or in the group's own org. Shadowing a bare catalog name in your own registry (a hardened `ubuntu-noble`) remains legal and deliberate, and the build names the serving location in its output; prefixed names cannot be shadowed accidentally, because the prefix is the group. The same rule covers every published artifact name, not just images (user decision, 2026-10-17): ranges and their build manifests, recipe bundles, and scenario images all use the one-slash grammar, with bare names reserved for the project's own catalog and examples, so a mirrored range lands as `other-group/their-range` and can never collide with yours. The six examples' upstream strings (docker tags with annotations, AMI names, Vagrant boxes, libvirt XML names) were provenance notes, not references; they move to `notes.md`/comments where they always belonged, and each range's translation gets real logical names as part of its build slice.

**Resolution order: pin, then local cache, then the registry search path.** An explicit `@sha256:` pin short-circuits everything. Otherwise the name resolves against the local image cache, then an ordered list of configured registry locations, first match wins (default `[docker.io/meridianlabsai]`; a deployment with its own registry prepends it, so its artifacts shadow public names deterministically). A registry location has three interchangeable forms (user decision, 2026-10-17): the public hub, a private OCI registry, or a plain directory in OCI image-layout format (the registry-less shape for air-gapped delivery; see [Journey B](build-images-journey-b.md)). The intended topology (user decisions, 2026-10-17): the public org carries only the reusable base tier (goldens, daemon bundle, common recipes); deployments run their own registry for their own pushed ranges, with the public org as the search-path fallback so connected deployments never need to mirror; mirroring is the move for disconnected fleets and for removing the Docker Hub availability dependency. A registry is never strictly required, since locally built artifacts in the cache satisfy resolution on their own. A name that resolves nowhere is `image-not-in-cache`, whose hint now says pull or build rather than derive-it-yourself. This is deliberately the recipe-references resolution discipline with a registry tier appended: one by-reference rule for both reference kinds.

**Freezing is automatic; moving forward is explicit.** Resolution is local-cache-first, so a bare name is sticky: once a build has fetched `ubuntu-noble`, later builds keep resolving to the cached artifact even as the registry moves on, and each build manifest records the digests it resolved (the lockfile, produced as a byproduct of building, never maintained by hand). Picking up newer artifacts is an explicit act, the Docker `pull`-to-refresh model: an update command re-resolves bare names against the registry search path and fetches what changed, and the next build's keys change accordingly, rebuilding proportionally per the Q2 algebra. An `@sha256` pin opts a reference out of even explicit updates; the update verb's name and placement is Q8's call.

**The name-to-digest binding is owned by the build, recorded in the manifest.** The spec stays human (names); the build resolves each name once and the build manifest records only `(name, digest)` pairs, satisfying range-build's digest-only rule. Between builds, what a bare name means at the registry tier is whatever the registry's tag currently points at, exactly like a Docker tag; reproducibility comes from the manifest, not from freezing names. A fleet pin file (names to digests, consumed as `@sha256` pins) is Q11 territory and nothing here precludes it.

**Per-guest boot variation gets typed spec fields, never name annotations.** The vulhub `(command: server)` smell dissolves: which service a guest runs is `services`/`provisioning` content under the current schema. If a genuinely image-level parameter ever appears, it becomes a schema field on the host, and the grammar still carries nothing.

**The local cache file-name rule survives as a layout detail, not an identity.** `image_file_name()`'s slug stays for cache layout; identity is the digest, and cache hits verify it (already true for goldens).

## Q2. One invalidation algebra

**Every artifact has two keys: a content digest (what it is) and a build key (what made it).** The build key is a canonical string of the kind plus the content digests of every input; the golden's existing key (`recipe:{RECIPE_VERSION}|vendor:{digest}|daemon:{digest}`) is already this shape and becomes the template rather than a special case. The regime per artifact:

| Artifact | Build key inputs |
|---|---|
| Golden | derive-recipe version, vendor digest, daemon bundle digest |
| Scenario image / recipe output | base image digest, recipe bundle digest, resolved vars hash |
| Checkpoint | every member guest's image digest, every applied recipe digest + vars, converged-spec content hash, CPU model |
| Realization bundle | spec hash, plan hash, resolved image digests (as today, unchanged) |
| Build manifest | all of the above (it is the record of the resolution) |

**Rebuild rule: an artifact rebuilds exactly when its build key changes, and a rebuild cascades only along the input edges.** The acceptance tests, from the requirements doc's driving cases: a recipe edit rebuilds that recipe's outputs and dependent checkpoints, never goldens; a daemon bump re-derives goldens and re-bakes checkpoints, never recipes; a vendor refresh is a new base generation; a spec edit re-renders only. Verification caches all-or-nothing (user decision, 2026-10-17): a build whose entire key set is unchanged may skip verification, reporting the recorded result and its timestamp; any input change triggers a full re-verify of the whole range, never a partial one (declarations interact across guests, so per-host verification is false economy); and `build --reverify` forces the full pass on demand. The skip never trusts a recipe, only our own recorded verification of bit-identical inputs, and two backstops bound it: artifact digests still verify on every cache hit, and the provider's per-sample health gates run at eval time regardless, so no agent lands on an unverified range. The known residual is environment drift (a host QEMU/kernel change with no input digest change), covered by the per-sample gates, `--reverify`, and CI running full verifies on blessed builds.

**The checkpoint key, elaborated (user decision, 2026-10-17).** The key is exactly the table row: member image digests, applied recipe digests plus vars, converged-spec hash, CPU model. Deliberately outside the key: capture time (age is freshness, not identity; the freshness cap is an additional rebuild trigger alongside key change) and QEMU/libvirt versions (the manifest's host-compatibility statement, checked at runtime; cold boot from converged disks is robust across hypervisor versions, and only the memory-restore opt-in cares). The converged-spec hash is a projection: only spec sections that realize inside guests participate, so an ACL or CIDR edit re-renders without rebaking a 17-minute forest; defining the projection precisely is slice work, the principle is decided. And rebuilds are always clean rebakes: boot fresh goldens, run all recipes, converge, capture. Restoring an old checkpoint, patching the changed recipe, and re-capturing is forbidden, because incrementally patched state is state no clean build can reproduce. This pre-answers the rebake half of Q6; what remains of Q6 is build caching across CI and laptops and the orchestration detail.

**The stale-bundle hazard closes with a named cause, not a new mechanism (ratified 2026-10-17).** The hazard: re-deriving a golden strands previously rendered bundles, surfacing as a bare digest-mismatch refusal at `up`. Two-part fix: (a) inside a build, rendering is the last step, so a build manifest can never contain the hazard; (b) for hand-run `render`, the `up` refusal gains cause detection: when the cache holds the same image name at a different digest than the bundle recorded, the message says the image was re-derived or re-pulled since render and the fix is re-rendering, in the existing hint style. Byte-determinism of render and the bundle digest definition (`sha256(manifest.json)`, range-host-v1) are unchanged.

## Q3 (core). The artifact ledger and the two manifests

**The ledger.** Each artifact, its identity, and whether it publishes to the registry:

| Artifact | Identity | Publishes |
|---|---|---|
| Vendor base | content digest | yes, as the bottom layer of golden chains (this is what makes disconnected mirroring complete) |
| Golden | digest + build key | yes, as a chained-qcow2 OCI artifact per [image-distribution](image-distribution.md) |
| Scenario image | digest + build key | yes, as a delta layer on its base's chain |
| Daemon bundle | digest + version | yes, as an OCI artifact (today's operator-carried `--daemon-sha256` ceremony retires) |
| Recipe bundle | digest per [recipe-references](recipe-references.md) | yes (a range that references it must be buildable from a mirror), resolution order unchanged: range dir, cache, registry |
| Checkpoint bundle | digest + build key, members individually digested | yes, as an OCI artifact whose members are plain blobs; memory images are not qcow2 chains and travel eager-pull only (lazy and CDC do not apply to them until measured need) |
| Realization bundle | `sha256(manifest.json)` | no: rendered on demand from built artifacts, shipped only through the host-provider seam's existing delivery modes |
| Build manifest | content digest | yes: it is the pull root, the one name an eval runner needs |

**The publish column, ratified (2026-10-17), with one posture note:** recipe bundles publishing makes recipes distributable artifacts, so the project's trusted-operator posture (integrity verified by digest, provenance not yet signed, no signing machinery before the distribution contract asks) extends to recipes explicitly, and vendored upstream automation inside published bundles carries its attribution per the existing [LICENSES.md](LICENSES.md) practice.

**Two manifests, settled as wraps-by-reference (ratified 2026-10-17).** The range build manifest (range-build's commitment: resolved `(name, digest)` images, recipe `(name, version, digest)` triples, verification results, seeds, checkpoint compatibility statement, capture time) is the publishable identity of a built range version. The realization-bundle manifest (format_version 1, implemented) stays exactly what it is: the runtime integrity document the applier verifies. The build manifest records the bundle digest when a bundle was produced, and nothing about the applier or provider changes. Names: **build manifest** and **bundle manifest**, used consistently from here on; the runtime-contract phrase "refuses to instantiate from a manifest whose digests it cannot verify" is true of both, each at its own layer.

**Consumption shape this fixes.** Journey B's endpoint becomes: `pull` (spec-driven by default: the local `range.yaml`'s normalized-form content hash selects the published build manifest whose recorded spec hash matches exactly, with `name@sha256:...` available when no spec is in hand; the provider runs the same pull automatically at eval init, Docker-provider style, so the explicit verb is preflight), verify, render inside the provider, `inspect eval`. The build manifest embeds the spec it was built from, so a pulled artifact set recovers to source without a git checkout. The mirror/sync command operates at the same granularity: mirroring a build manifest mirrors its transitive references, to a private registry or an OCI-layout directory alike, which is what makes a disconnected fleet's copy complete by construction. The target transcripts are [Journey A](build-images-journey-a.md) (author) and [Journey B](build-images-journey-b.md) (publish, mirror, consume).
